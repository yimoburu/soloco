# Founder outcome implementation

Approved direction: the founder can leave, return and receive useful progress.
Source candidate: v0.7.6. Previous v0.7.5 company pins remain compatible; semantic writes fence older runtime writers. No installation or adoption is performed.

Implementation base: `7b6d6d5`, preserving the concurrent backlog fixes.

This candidate connects outcome framing, prospective proposal handling and typed
recovery to existing runtime contracts. It preserves the separate development,
review, handover and execution permissions. It does not infer company adoption
or customer value from source tests.

Acceptance work:

- Explicit task outcomes retain objective, expected effect, observation,
  assessment period and exact supplied evidence through dependencies/checkpoints.
- Opt-in read-only operating proposals can feed subsequent work without changing
  accepted knowledge. Legacy outputs, notices, failures, unknown fields and
  changed obligations retain their conservative reconciliation path.
- Only typed capacity/resource holds can leave an unstarted task eligible for
  later scheduling. Unknown errors and uncertain attempts never auto-retry.
- A supplied-feedback workflow links proposed improvement, retained candidate,
  actual tests, independent review and observed feedback, preserving unmeasured
  business effects and founder time as unknown.
- Retained evaluations distinguish mechanical contracts, actual native behavior,
  human observation and adoption. Current capability reporting links exact proof.

Validation and remaining boundaries are recorded here after execution.

Review repairs retain unresolved proposal attempts and exact admitted input bodies
across successor publication and owner replacement. Handover includes queued,
running and failed attempts with their actual closure state. This release keeps
those attempts conservatively; it does not provide automatic historical pruning.
Nonautomatic readiness failures require attention, including before queueing;
resource contention remains a typed automatic wait for an unstarted task.

The installed Codex 0.154 startup diagnostic about its unknown `ultrafast_mode`
requirement is retained as a warning only before the first turn. Arbitrary error
items, malformed sequences and absent/failed completion still reject the result.
Native evaluator wire output is retained so failures can be diagnosed without a
new call. Applied model controls remain separate from effective speed/price.
