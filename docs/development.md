# Developer guide

The [README](../README.md) covers installation and the current release boundary. [SPEC.md](../SPEC.md) is the target contract; the plugin implements preparation, review, file-only prototypes and bounded local development candidates, not a claim that every acceptance criterion passes.

The target covers ongoing operation against founder-defined objectives, including profitability and founder workload where relevant. Launch and financing are optional milestones. The current plugin can prepare objectives, operating plans, and reviews from supplied evidence; it does not run business operations, collect live business metrics, or schedule unattended operating reviews. Existing companies keep their pinned governance until explicit adoption through the upgrade flow.

v0.6.6 adds conservative whole-body aliases for duplicate historical upgrade reports and a current-state projection preview. Every unique body remains compulsory, all occurrence context and original records survive, and aliases confer no authority or evidence delivery. The 600,000 ms call ceiling, immutable 45-minute deadline, model controls, independent review and governance are unchanged. Source integration remains unsupported by `company_develop`; authorized repository maintenance is separate. Installation preserves existing compatible pinned teams, including v0.6.5.

## Design rule: less is more

`SPEC.md` contains enduring rules only. Keep role catalogs in `assets/roles.json`, CoS procedures in its skill, runtime limits in code and this guide, installation/capabilities in the README, and optional examples in playbooks. The bundled governance is generated, never independently authored. These implementation documents do not add a second constitution or override a company's adopted rules.

Choose the smallest change that satisfies a concrete need and the contract. Reuse existing records, tools and workflows; avoid speculative abstractions, duplicate sources of truth and extra coordination layers. Remove obsolete machinery. Preserve authority, independent review, evidence and continuity when simplifying. Verify the relevant behavior, including failures; do not add procedural checklists merely to restate the code.

## Plugin structure

`plugins/soloco/` is self-contained. The repository's `.agents/plugins/marketplace.json` and `.claude-plugin/marketplace.json` distribute the same package to Codex and Claude. `.codex-plugin/plugin.json` explicitly selects `.mcp.codex.json`, the Codex hooks and skills; `.claude-plugin/plugin.json` and `.mcp.json` supply Claude's format. Host-specific hooks share the runtime. Product, repository, marketplace and plugin are named SoloCo/`soloco`. Internal `company_*` tools, the `company` MCP namespace, `COMPANY_PLUGIN_DATA` and `.company/` remain stable because they describe company entities and preserve pinned instructions. They are not a second product or installable legacy plugin.

| Component | Responsibility |
|---|---|
| `skills/soloco/` | Chief of Staff interview, coordination, reviewed proposals, and founder communication |
| `skills/setup/` | Readiness without creating a company |
| `scripts/run.sh` | Use compatible Node or install checksum-pinned Node 22.22.0 privately; no npm dependencies |
| `runtime/hooks.mjs` | Read-only Codex discovery and binding diagnosis; backed-up removal of recognized project hook duplicates |
| `runtime/main.mjs` | Startup hooks and the stdio MCP tool interface |
| `runtime/store.mjs` | SQLite transactions and persistent company state |
| `runtime/engine.mjs` | Coordinator ownership, records, assignments, notices, pause, and handover |
| `runtime/develop.mjs`, `local-sandbox.mjs` | Standing local scope, candidate generation, isolated Node test workers, receipts and independent acceptance |
| `runtime/prototype.mjs` | Immutable prototype scopes, attributed authorization, exact-bundle review, and exclusive local file creation |
| `runtime/upgrade-evidence.mjs` | Frozen semantic projections, deterministic pages, source registry, exact excerpt retrieval, independent delivery ledgers and prompt budgets |
| `runtime/upgrade.mjs` | Candidate inspection, native CoS/QA continuity checks, explicit adoption, verification, and definition recovery |

| `assets/` | Bundled governance and the canonical proposed role catalog |

The Chief of Staff decides what to assign; software commits records and runs sessions. There is no second coordination agent or founder connection service. Role sessions use explicit native IDs, not `--continue`/`--last` or parent-owned subagents. Peer messages enter durable role inboxes and are included on the recipient's next assignment; a message does not wake a role independently of Chief of Staff scheduling.

## Records and authority

The attached folder contains `.company/company.sqlite` and SQLite's companion files while active. The database stores identity, pinned governance and role definitions, draft intent/plans/preferences, author-attributed artifacts and exact-version reviews, jobs, native session references, messages, notices, and an event index. Use Company tools to inspect or amend it. Keep `.company/` private; back up using SQLite's backup facilities or after all connections close, rather than copying a live database file alone.

Initialization preserves existing project files. A legacy `team/manifest.json` is detected and held for explicit migration; it is never silently imported or overwritten. Company records remain outside install/cache paths. An unsupported schema/runtime combination holds ordinary mutation. `runtime_version` records the runtime that created, migrated, dispatched new assignments, or introduced new prototype records into the state; `executing_runtime_version` in status identifies the running code. An explicit tested compatibility list lets v0.6.6 operate schema-2 states produced by v0.2.0/v0.2.1/v0.2.2/v0.3.0/v0.3.1/v0.4.0/v0.4.1/v0.5.0/v0.6.0/v0.6.1/v0.6.2/v0.6.3/v0.6.4/v0.6.5 without rewriting pinned definitions or triggering team adoption. No future version is accepted merely because its version number looks compatible. The explicit upgrade flow supports schema-1 v0.1.0 preparation records and schema-2 records produced by v0.2.0, v0.2.1, v0.2.2, v0.3.0, v0.3.1, v0.4.0, v0.4.1, v0.5.0, v0.6.0, v0.6.1, v0.6.2, v0.6.3, v0.6.4 or v0.6.5; it does not silently adopt definitions or migrate arbitrary formats.

Startup hooks bind the host session ID and attached folder in private plugin data. Only the current coordinator may mutate ordinary records. A second chat can read status, pause, or perform an explicitly requested handover after active assignments are held. Handover increments the ownership epoch and retires old role instances; successors use company records. Pause requests process cancellation through the worker, but provider completion, descendant processes and worker-death termination are not guaranteed. Late, outdated, or revoked results are quarantined and cannot become acceptance.

All artifacts remain proposals or submissions. An independent review verdict applies to one draft version and supplies no gate Pass, role qualification, or external-action permission. Author identity and version checks are structural; reviewer expertise and evidentiary sufficiency still require evaluation. The founder host remains permissioned by its own app. Local filesystem access can bypass the record store; this is not hardened multi-user isolation.

Workers run without business execution tools: Claude's built-in tools/MCP servers are disabled; Codex uses a read-only sandbox, disabled shell/peer-agent/web tools, and isolated working directories. The runtime limits concurrency to three. Per-assignment execution limits, separate queue/startup limits and cancellation follow the timeout policy below. The runtime preserves failures and never automatically retries uncertain results. Company tools expose no arbitrary shell or external-action endpoint. Native provider history lives with the host; it is not portable company memory.

Notices track presentation attempts, seen status, and resolution separately. Startup/prompt hooks present pending notices even if the Chief of Staff did not request them; chat-context presentation is not proof of human receipt. The literal founder message `pause` directly holds company work. Natural-language controls are recorded by the Chief of Staff and are not independent human-authentication proofs. No notice or control can grant venture execution in this release.

## Local development implementation

`company_develop` provides `inspect`, `plan`, `authorize`, `run`, `accept` and `revoke`. New development needs an adopted v0.5.0, v0.6.0, v0.6.1, v0.6.2, v0.6.3, v0.6.4, v0.6.5 or v0.6.6 team and exact current v0.18 governance; installation does not adopt them. Company mode stays preparation: authority is attached to the specific standing local scope, never to a global unrestricted mode. Separate company objectives, source/data choices, expiry and attempt/time/output limits from framework identity, integrity and independent-review enforcement.

A scope snapshots explicitly selected UTF-8 source files and hashes, exact editable/new paths and Node test paths, acceptance, stop conditions and data policy. Planning requires the founder's source instruction and `model_data_approved: true` before reading or returning source contents; later authorization records the exact work scope. Do not defer source-sharing consent until after the bytes have reached a model. Current capability ceilings are 32 paths, 100,000 bytes, 10 generation attempts, 120 seconds per test run, 100,000 output bytes and thirty days. Company choices may be narrower. Source sharing with the configured model host is explicit; no synthetic-only rule applies here. Data classification and semantic acceptance require founder/reviewer judgment.

`company_dispatch development_id` starts fresh Engineering candidate generation. Runtime builds a retained copy under `.company/development/`; the original source stays unchanged. It checks exact paths, original source hashes and candidate contents. A run reserves a durable job and launches a detached worker, leaving MCP available for pause/revoke. The fixed Node runner executes in an available macOS OS sandbox plus Node permissions. Unsupported isolation fails closed. Tests have read-only candidate source and scratch-only writes, no network or child processes, sanitized environment, time/output bounds. Hard memory and disk quotas are not implemented. This is a local test boundary, not a hardened multi-user store or a promise to contain kernel/runtime vulnerabilities. Full sandbox details and adversarial checks live with `local-sandbox.mjs` and its tests.

Runtime receipts record the candidate, exact test paths/configuration, isolation result, exit/output, elapsed time and hashes. QA reviews the exact receipt and automatically supplied candidate/scope. Acceptance requires a genuine passing test-job receipt and a current independent QA Pass bound to candidate and receipt hashes. A model-written test claim is never a receipt. Zero exit alone does not establish coverage or correctness; QA assesses relevance. Accepted output remains a local candidate, not source integration, a commit, installation or deployment.

Startup and the separate test watchdog each probe the selected trusted Node executable for `--test-isolation=none`, falling back to `--experimental-test-isolation=none`. This supports compatible Node 22 sandbox launch as well as newer flag spellings. Each probe evaluates only a fixed empty expression outside the candidate directory, with a scrubbed environment, a one-second timeout and a 10,000-byte output bound. The selected spelling is cached per process and used with the existing sandbox and Node permissions. If neither spelling works, execution fails closed with a diagnostic; candidate code never runs outside Seatbelt.

The grant binds scope, ownership/team and governing intent/decisions. Routine failures and review results do not revoke it; all remain evidence in fresh assignment context. Repairs consume remaining attempts. Changed original inputs, boundaries, expiry, pause/revocation or ownership prevent acceptance. Tests recheck eligibility while running and stop on cancellation. An uncertain or interrupted run retains its intent and holds further work until inspected; no automatic retry. Test workers count toward existing active-job limits and continuity checks. Failed output envelopes retain bounded rejected evidence and precise errors on their jobs; they never route partial messages or become accepted artifacts.

## Local prototype implementation

`company_prototype` adds `inspect`, `plan`, `authorize`, `revoke` and `materialize`. Company mode stays `preparation`; permission belongs to one immutable scope. Status and startup hooks distinguish installed support from company eligibility. v0.6.6 accepts adopted v0.4.0/v0.4.1/v0.5.0/v0.6.0/v0.6.1/v0.6.2/v0.6.3/v0.6.4/v0.6.5/v0.6.6 teams with the exact v0.17 or v0.18 governance. The previous governance hash is explicitly retained for compatibility; arbitrary older or modified governance remains unsupported. Installation neither adopts new rules nor invalidates an existing compatible prototype grant. Old pinned teams remain usable for preparation, but reviews or generic decisions cannot unlock prototype writes. Prototype records stamp the producing runtime version; old packages cannot operate new-team state.

A plan records a new `prototypes/<slug>` directory, 2–32 exact relative file paths, test paths, manually supplied fictional fixtures and their source, acceptance, stop conditions, expiry (up to seven days), and 1–3 implementation attempts. Hidden paths, traversal, host instruction files, case collisions and file/directory conflicts are rejected. Independent QA must approve the exact scope before `authorize` records the founder instruction and fictional-data attestation. Company records still supply assignment constraints; no project-data ingestion is added. Fixture provenance and fictional content are attested and reviewed, not mechanically proven. This provenance boundary is the same as existing founder controls: the runtime validates the recorded grant, not human intent or fixture truth independently.

`company_dispatch` with `prototype_id` starts a fresh `engineer` native session, reserving one attempt. It includes the full scope, fixed restrictions, company constraints, failed reviews and notices. The unchanged adapters expose no shell, file or external-service tools. The worker returns complete file contents; the runtime adds fixtures unchanged and validates exact paths and a 100,000-byte bundle ceiling. Unsupported/blocked output fails visibly. Test files are required but not executed; their adequacy and semantic behavior are QA judgments, not guarantees from the structural checks.

A separate `qa` session reviews the bundle. Its structured verdict must identify the scope and bundle hashes, explicitly permit `materialize_local_prototype`, contain no blockers, and state `tests_executed: false`. Plan review similarly permits `authorize_local_prototype`. Actual native-session identity is checked against the author, in addition to role-instance separation. A prior negative review blocks that exact candidate; a repair is a new artifact within remaining attempts. No automatic retry occurs.

Materialization checks authorization, ownership, expiry, dependencies and exact review before recording durable write intent. It creates a fresh destination, exclusively creates permitted files, reads them back and records hashes. It never edits existing files, executes code, installs packages or uses new services. Interrupted/failed writes retain their receipts and possible partial files for inspection, without automatic retry or deletion. Receipts describe the completed readback, not perpetual file integrity. As elsewhere, same-user filesystem access is outside the isolation boundary.

Changes to company constraints or unresolved notices hold the grant; ordinary delivery/seen bookkeeping does not. Pause/revoke fence late results. Handover/team upgrade changes ownership and invalidates old grants while preserving their records and local files. The existing team-upgrade continuity checks carry these records but grant no new prototype authority. Running tests, integrating a prototype or exposing it externally requires a separately supported workflow, not another Pass on this file-only contract.

## Checked team upgrades

`company_upgrade` exposes `inspect`, `prepare`, `apply`, `verify`, and `recover`. `inspect` returns the candidate hash, instruction/governance differences and a current-state projection preview without authoritative-state mutation. It retains existing `withStore` opening semantics, including possible SQLite/WAL initialization writes; it does not promise physical filesystem read-only access. The preview builds baseline v1 and candidate v2 streams from identical current checkpoint/history inputs, appending the current upgrade (including a terminal attempt) as next-attempt history. It returns only projection counts, hashes and net UTF-16 character/page differences, without model, readiness or catalog calls or authoritative transactions. Prepare adds a decision record, so these counts are not an exact reservation or time forecast. `prepare` requires that hash, the current ownership epoch, and the exact founder instruction; changed governance also requires a separate source instruction. A different founder chat requires explicit takeover and a paused company; the same mechanism allows recovery when the previous coordinator disappeared during an upgrade. CLI readiness/authentication must pass. Active assignments must finish or be cancelled before preparation.

Only `prepare` accepts optional `model_selection`, reusing dispatch's schema, `normalizeSelection` and adapter catalog validation. Invalid model/effort/speed controls reject before the preparation transaction or readiness check; other actions reject selection outright. This maintenance input is independent of the pinned team's ordinary dispatch eligibility. Omission avoids catalog discovery and keeps the legacy null adapter argument; deliberate defaults are also supported. The exact normalized request and its hash are saved on the attempt, with catalog metadata kept separately. The worker freezes and checks that request throughout review, pins its hash in evidence, and apply/verify recheck it. Legacy attempts without selection fields remain supported under their existing eligibility and deadline checks. Selection changes require recovery and a fresh authorized prepare, never continuation of failed/expired review.

Every CoS and independent QA native call receives the same saved selection, including retrieval, replay and synthesis. Call records retain `model_selection` as requested settings and `model_evidence` as adapter-returned observations and applied controls. If execution throws, including timeout, observations and applied controls are recorded as unknown; requested settings never fill those fields. The adapter currently provides applied-control evidence only with successfully parsed native output. Codex does not report the answering model; Claude model usage is cumulative session evidence. Catalog support and launch flags do not establish effective provider settings, account entitlement, review quality or completion time. No policy default, paid tier, timeout extension, automatic retry or session restart is introduced.

Preparation snapshots business state, preserves previous definitions, pins the candidate, increments ownership, and moves to schema 2. Old v0.1.0 coordinators reject schema 2, even if they refresh their epochs. Compatible current-runtime coordinators reject ordinary mutations during the upgrade. Both coordinator instructions and specialist charters are pinned in state; startup hooks provide only upgrade guidance until adoption/recovery permits normal work. `compat/company-0.1.0.md` is the immutable CoS skill from commit `a5590b6`, used to recover the shipped legacy definition that v0.1.0 did not persist.

A detached worker starts a fresh candidate CoS native session and a distinct independent QA native session. Each role resumes its own ID through the real adapter; unexpected identity changes fail closed. A frozen semantic JSON stream includes every checkpoint field, keyed record/job, notice/message, previous revision and unknown prose, plus prior attempt reports/errors/verdicts. It is split deterministically into consecutive UTF-16 pages of at most 120,000 units (envelopes and JSON escaping count toward the full request budget). Boundaries can split JSON tokens; page offsets and hashes permit exact reassembly. Pages supply precomputed excerpt citation ranges, so tool-less models never need to calculate hashes. Only structurally recognized file/source/log/machine bodies become immutable references. Unknown maps are semantic; string maps require portable directory paths or recognizable file names, while explicit file objects carry their own schema. Dotted prose such as `Founder rule.` and unknown dotted identifiers such as `budget.max` stay semantic. Prior full checkpoint/team snapshots become references; originals stay in `upgrade_history`, whose complete hash is bound and rechecked on apply and verify. There are no recursive full-history copies.

Transport `soloco-upgrade-evidence-v2` / prompt protocol `soloco-upgrade-pages-v2` indexes whole artifacts only at history-attempt `cos_pages[*].artifact`, `qa_pages[*].artifact`, `probe.artifact` and `review.artifact`, paired with `calls[*].text` within that same attempt. Matching requires equal nonempty native identity, expected role/phase and strict serialization of the entire artifact (at least 4,096 UTF-16 units), including unknown fields. The existing whitespace helper in strict token mode removes JSON formatting whitespace outside strings, without parsing or normalizing call bodies. Exact indexed token equality refuses duplicate keys, lossy/noncanonical numbers, alternate escapes, key reordering and malformed outputs. Legacy record-content decoding retains its existing escape behavior.

The first matched body remains compulsory inline in its original string/object representation, with no recursive payload extraction. Later bodies carry `evidence_body_alias`, direct `target`, `representation` (`json-text` or `json-value`) and `body_sha256`. Registry `body-occurrence` descriptors bind scope/path, owner source, raw hash/length/encoding, token hash/length and delivery kind (`compulsory-inline` or `alias`); targets are always earlier inline occurrences, never aliases. Validate descriptors at the exact generated occurrence path, not by a reference-looking object's shape. Source-supplied lookalikes stay literal. `resolveBodyAlias` accepts authentic frozen generated aliases only and returns complete tokens/object without delivering evidence. Original native text stays exactly retrievable, including whitespace needed for byte-exact reconstruction. Source/history/checkpoint originals and hashes are unchanged; occurrence metadata/order remain separate. Aliases mean body equality only, never review agreement, blocker resolution or authority.

Delivery of an alias does not deliver its target body or original source. Existing citation guards and per-role delivery ledgers are unchanged: cite only actually delivered ranges, including the target's stream range when supporting shared-body claims. All pages still go independently to both roles. Keep findings page-specific and avoid recopying long reports, while retaining every distinct constraint, blocker and uncertainty and complete final reconstruction. No new semantic finding cap, output budget or adoption permission is introduced.

CoS returns durable findings with exact citations for each page. Before final synthesis, findings replay through the same session in batches measured against the complete assembled prompt plus response reserve. All findings use one replay call when they fit; larger sets use consecutive bounded batches without trimming or reordering. Each successful batch retains a receipt binding its exact findings hash, page IDs and native ID; apply rechecks complete replay coverage. Independent QA receives every raw semantic page, its CoS findings and the bounded proposed handover, and records a page review. QA findings and their complete union of page blockers replay in the same bounded batches before its final permission decision. Software verifies the complete inventory/page coverage; models reconstruct substantive constraints, unresolved work and next action, each with evidence citations, rather than echoing every historical ID. QA judges the truth of those claims. A QA page Pass permits only `continue_upgrade_review`, with no adoption authority. Replay acknowledgements grant no permission and cannot replace earlier page reviews. Age or a later Pass never clears an earlier page Blocked/Fail. Only after every page Pass may the final synthesis permit adoption. Final Pass must explicitly permit `apply_preparation_team` without unresolved blockers; withheld permission fails closed. These checks do not establish professional qualification or guarantee model judgment. Preserving older governance can correctly block adoption on stricter requirements; explicit governance adoption remains required to change those rules.

Every prompt includes a phase-specific `response_contract` with the exact required JSON shape and ready-to-copy citation metadata. Page, replay and synthesis artifacts require top-level `content` and nonempty `citations`; nested findings alone are invalid. Synthesis additionally requires evidence-cited `continuity`; QA page/final responses require their distinct review permissions. Replay requires a cited acknowledgement, without a review permission. Retrieval returns to the original phase contract. The alternative reads-only envelope has exactly one top-level key, `reads`, and no artifact fields. The tool-less JSON protocol accepts `{reads:[{source_id,sha256,offset,length}]}`: 1–4 exact frozen ranges per response, at most 32,768 UTF-16 units per range and 16 read rounds per task. Returned excerpts carry source and range hashes. Software-built pages/reads confer no citation permission until successfully delivered to the matching native session. Author and reviewer have separate delivery ledgers; exact delivered partial ranges can be cited without reading an entire multi-megabyte payload. Hash/revision mismatches, unseen pages, gaps and surrogate-splitting boundaries reject citations. Rehearsal models have no filesystem or external tools.

Every complete prompt (instructions, authority, envelopes, escaped page/read bodies and QA author report included) plus a 40,000-character response reserve must fit 900,000 UTF-16 units. Responses are independently bounded. Traffic counts use safe cumulative integers with no one-million-character lifetime cap. Retained call measurements include characters and approximate tokens (`ceil(characters/4)`); they do not guarantee model token fit. The native harness manages its active context. Codex documents automatic compaction/model defaults at https://learn.chatgpt.com/docs/config-file/config-reference; Claude documents headless resume/context management at https://code.claude.com/docs/en/headless and https://code.claude.com/docs/en/context-window. No compaction is claimed unless observed; synthetic CLI tests do not demonstrate live Claude behavior. Host failures hold with diagnostics and are not retried.

New rehearsals use one immutable 45-minute deadline, including all pages, retrieval, replay and synthesis. Each native call receives `min(MAX_EXECUTION_TIMEOUT_MS, deadline_ms - Date.now())` (at most 600000 ms) and an overall deadline abort signal; less than 1000 ms remaining fails before a native call. Old pending attempts without that field retain the seven-minute fallback. Before the first model call and before/after calls, retrieval and accepted publication, the worker checks that the saved checkpoint hashes to the original pin, rejects changed pins against the frozen evidence subject, and rechecks live checkpoint/history hashes, owner/epoch, pause, current attempt, installed/stored candidate and deadline. Late or malformed responses and native identities remain journaled but grant no permission. `company_wait`/`company_status` expose bounded progress/traffic summaries. New business facts invalidate review; delivery-attempt bookkeeping does not.

`apply` requires a passing exact-checkpoint review and unchanged installed candidate. Both `apply` and `verify` independently hash the saved checkpoint and check its pin against frozen evidence; corrupting that snapshot cannot omit a fact from rehearsal or readback. Recovery stays available for an invalid saved checkpoint and preserves later business facts. `apply` atomically pins the adopted definitions, retires specialist references, and revokes the previous ownership epoch. `verify` is a separate post-commit readback of company identity, preserved records, obligations, notices, and other checkpoint fields. Normal work and resume remain held until it passes. The CoS reloads its pinned brief; specialists cold-start on their next assignment. The two probe sessions test preparation continuity; they are not the founder's chat or a claim that every future specialist has been live-tested.

`recover` restores prior definitions under the installed supported runtime, retires sessions again, and retains later evidence, messages, notices, and upgrade history. It leaves the company paused for a checked resume. No database rollback occurs, and the old v0.1.0 binary cannot operate the migrated schema. Natural-language upgrade/takeover instructions use the same source-attribution boundary as existing controls; they are not independent human authentication or external-action approval. Same-user filesystem access remains outside the security boundary.

## Assignment context

The shared specialist prompt assigns ownership of deliverable quality and completeness to both authors and reviewers. It requires independent domain judgment, evidence, uncertainty and blocker disclosure, and repairs within existing authority and attempt limits. This implements the contract's role accountability without changing pinned governance, granting tools or waiving failed reviews.

Dispatch snapshots the input versions and a hash of the full supplied context. The pack includes pinned governance, the assigned role, company identity/mode, all intent/decision/preference records, failed or blocked reviews, unresolved founder notices, the role's inbox and explicitly named inputs/review target. The CoS supplies relevant plans and evidence via `input_ids`; it must not rely on unstated session memory. Prior record revisions are retained in selected records.

Unrelated artifacts are not included. New or changed constraints, selected inputs, unresolved notices or incoming messages invalidate the result; notice presentation/seen bookkeeping does not. Queued jobs check their context before invoking a model, and returned results recheck before acceptance. Legacy queued jobs establish their complete context at startup. Packs over 200,000 characters fail visibly; the runtime never silently slices a record. Full continuity rehearsals use the separate paged evidence protocol and per-request budgets described above; ordinary assignment limits remain unchanged.

## Model selection

Model selection uses existing dispatch, adapters and job records; there is no routing service or second database. The CoS assesses model, effort, speed and a separate timeout against task complexity, ambiguity, consequence of error, input/output needs, latency and relevant prior outcomes. ## Observed DAG and chronology

`company_progress({root, session_id, format?, recent_jobs?, render_id?})` reads the bound store without reconciliation or mutation. Formats are `json` (default), inline `html`, literal `text`, and `mermaid` (diagram plus equivalent text). `recent_jobs` is 1–50, default 20. Status/wait keep their existing payloads and reconciliation behavior. No service, database, scheduler or new authority is introduced.

`progress.mjs` is the pure diagnostic foundation; `progress-view.mjs` whitelists public fields before projection and selects a bounded history. All active work and notice-associated producer jobs remain; prerequisite expansion adds up to 100 jobs. Public output caps evidence at 200, edges at 300, events at 300, diagnostics at 100 and input labels at 40 per job, with omitted counts. Full task instructions are excluded; only explicit task summaries (up to 160 characters) are labels. Expected outputs cap at 300 and planned handoffs at 200. All unresolved notice IDs/kinds/references and exact summaries remain, even when this exceeds ordinary history bounds. Full tasks, record contents, candidate/quarantine files, rejection bodies and review prose are excluded. Use authoritative job/record IDs for detail.

Input and review arrows require exact current revisions and resolved producers. Founder-authored intent/decision/preference records without producer jobs are context. Software candidate arrows require the canonical candidate ID, plan, nonempty candidate hash, candidate run job binding and, for returned tests, matching runtime receipt/hash/artifact bindings. No timestamp or planned-handoff inference is used. Cyclic edges are excluded with diagnostics. Edges describe evidence use, never scheduling or active waits. Recorded QA Pass and nested runtime receiver acceptance are separate facts; partial structural binding checks do not verify current authorization, reviewer independence or full review validity.

New dispatches optionally accept `expected_deliverable` (300 characters) and receive runtime-attributed requester metadata (owner role/session/host/epoch). Both fields enter new assignment contexts when present; omission leaves existing format-2 serialization/hashes unchanged. Native IDs come from observed jobs, never role names or fabricated sessions. Software jobs have no native agent identity.

HTML requires a caller-supplied `render_id` unique per mounted fragment (1–64 ASCII letters, digits, underscores or hyphens, starting with a letter). The pure renderer accepts it as `renderProgress(snapshot, "html", {renderId})`. All root, work-anchor and CSS IDs use that namespace; handlers look up the root by ID even if the host relocates scripts. No global counter or random identity is used. The renderer uses escaped text, no network assets or external actions. DAG cards show role, task, status, expected/returned output and recorded requester provenance; native identities, exact evidence and hashes, coverage and diagnostics remain in expanders. Cards wrap into readable evidence layers at narrow widths without internal scrolling or scaled text; chronology stacks below the DAG when space is limited. Event links/buttons highlight current work only. Literal text carries equivalent facts when inline HTML or scripts are unsupported; Mermaid labels are numeric entities. Host-local selection never invokes tools. CoS refreshes after meaningful observed changes during conversation; this is not unattended monitoring. Native host visual inspection and independent QA remain separate from deterministic rendering tests.
